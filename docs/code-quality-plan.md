# 코드 품질 보완 설계

## 범위와 적용 상태

후속 반영: 로딩 문구 순환 제거, 결과 ID 임의 생성 제거, 평가 CLI 공통 어댑터 사용과 입력 검증을 적용했다. 상세 동작은 [피드백과 생성 평가](feedback-and-evaluation.md)를 참고한다. 아래의 미사용 구조 제거·실험 정책 변경·요청 중복 방지는 여전히 후속 과제다.

컨벤션 적용과 동작 변경을 구분한다. 이번에 적용한 것은 변수 선언 분리, 역할에 맞는 이름, import 정렬, 제어문 중괄호, lint/format 검사이다. 동작에 영향을 줄 수 있는 로딩·실험 정책·미사용 구조 제거는 아래 설계 단계에 있으며 아직 적용하지 않았다.

평가 코드의 명시적 `any`, 빈 catch, 이미지 어댑터의 미사용 지역 변수는 정리했다. 평가 점수는 숫자 범위·누락·notes 형식을 검사한 뒤 합계를 계산한다. 이 변경에는 회귀 테스트를 추가했다.

## 1. 진행 상황을 가장하는 로딩 메시지 — 우선순위 P0

**문제:** `src/app/generating/page.tsx`는 실제 상태와 관계없이 1.4초마다 문구를 바꿔 약 4.2초 뒤 “거의 완성”을 표시한다.

**설계:**

- 문구 순환 타이머를 삭제하고 요청 중에는 “코디 이미지를 생성하고 있어요”만 표시한다.
- 대기 시간 안내가 필요하면 실제 경과 시간만 표시한다. 예상 완료율이나 예상 남은 시간은 제공하지 않는다.
- 클라이언트 상태를 `idle / pending / succeeded / failed`로 구분한다. 요청 생명주기는 생성 Hook이 담당하고 화면은 상태를 표시한다.
- 요청 시작 시 실패 상태 초기화, 실패 시 오류 안내·재시도, 성공 시 결과 화면 이동으로 전이를 제한한다.
- 화면 이탈로 인한 AbortError는 오류 화면으로 처리하지 않는다. 클라이언트 중단이 외부 생성 비용 취소를 보장하지 않음을 운영 문서에 기록한다.
- 재시도는 사용자 행동으로 한 번만 실행한다. Strict Mode의 effect 재실행과 연속 클릭에 대비해 후속 API 요청 키를 도입하고 서버에서 중복 요청을 묶는다. 파일 저장 유지 시 생성 ID와 별도로 요청 키의 원자적 선점이 필요하다.

**대상:** 생성 페이지, `use-generate-styling.ts`, styling store, `/api/generate`.

**완료 기준:** 느린 응답에서도 “거의 완성”이 나타나지 않고, 실패/중단/재시도/중복 요청에 대한 테스트에서 상태 전이와 provider 호출 횟수가 일치한다.

## 2. 검증 가설이 없는 프롬프트 분기 — 우선순위 P1

**문제:** `CONTROL`만 “Keep styling simple”을 추가하고 나머지는 모호한 강조를 추가해, 문장 순서와 내용 변화가 섞여 있다. 어떤 변화가 효과를 냈는지 해석하기 어렵다.

**설계:**

- 기본은 하나의 운영 프롬프트다. 실험은 명시적으로 활성화했을 때만 노출을 나눈다.
- 첫 실험은 두 후보만 사용한다: 동일한 보존 지시와 스타일 지시의 순서만 교환한다. 선택 조건과 수정 지시는 동일하게 유지한다.
- “보존 지시를 먼저 제시하면 인물 보존 실패가 줄어드는가”를 검증 가설로 둔다. 이 실험은 전체 프롬프트 개선보다 순서 효과만 검증한다.
- 새 `experimentId`와 프롬프트 버전을 기록하고 기존 `adaptive-v2` 데이터는 합산하지 않는다. API 통계도 실험 ID 단위로 조회한다.
- 초기 비교는 고정 50:50 무작위 배정으로 진행한다. 반응에 따라 노출 비율을 바꾸는 bandit은 비교 실험 종료 뒤 별도 운영 정책으로 도입한다.
- 오프라인 평가는 같은 원본·조건으로 두 후보를 반복 생성하고 사람의 블라인드 비교로 AI 평가의 오류를 확인한다. 생성의 확률적 변동과 작은 표본을 보고한다.
- 온라인 지표는 초기 생성별 착용 의향, 인물 보존 관련 수정 비율, 무응답 비율을 구분한다. 수정 요청은 자동으로 실패 보상이 되지 않는다.
- 효과 크기·표본 수·판정 규칙을 실험 시작 전에 정한다. 표본이 부족하면 우승 후보를 선언하지 않는다.

**대상:** `adaptive-prompt.ts`, 정책, GenerationRecord, 저장소 통계, 평가 CLI.

**완료 기준:** 두 후보의 차이가 지시 순서뿐임을 테스트하고, 이전 버전/수정 결과가 실험 집계에 섞이지 않는다. 고정 fixture 실행에서도 운영과 평가가 동일한 prompt builder를 사용한다.

## 3. 실행에 연결되지 않은 구조 — 우선순위 P1

**문제:** `ChooseVariant`, `ProductionPrompt`, `StylingPromptPort`가 현재 생성 경로에 연결되어 있지 않다.

**설계:**

- `ChooseVariant`는 삭제하고 현재 생성 유스케이스의 정책 호출을 단일 진입점으로 유지한다.
- `ProductionPrompt`와 해당 클래스만 사용하는 `StylingPromptPort`를 제거한다. 운영 프롬프트는 실제로 주입되는 `AdaptiveStylingPromptPort` 경로로 통일한다.
- 이미지 제공자·실험 저장소 Port는 외부 I/O와 테스트 대체에 사용되므로 유지한다. 디렉터리 전체를 새 아키텍처로 재구성하지 않는다.
- S3 어댑터는 미연결 선택 기능이다. 실제 배포가 S3를 사용하기로 결정되면 연결하고, 그렇지 않으면 별도 정리 변경에서 제거한다. 사용 계획이 확정되지 않은 상태에서 활성 저장 경로처럼 소개하지 않는다.

**완료 기준:** 제거 대상 참조가 없고 생성·피드백 회귀 테스트와 빌드가 통과한다. 설명 문서에 실제 실행 경로 하나만 남는다.

## 4. 이름과 선언 방식 — 컨벤션 적용 완료

`fd → formData`, `r → router/imageResponse`, `c → abortController/context`, `a → downloadLink`처럼 역할에 맞게 변경했다. 선언 하나당 변수 하나, import 정렬, 타입 전용 import, 중괄호를 lint로 검사한다.

**유지 기준:** `npm run check` 통과. 이름의 의미와 함수 책임은 리뷰에서 확인한다. 읽기 쉽다는 이유로 모든 함수를 클래스화하거나 모든 JSX 조각을 컴포넌트화하지 않는다.

## 5. 타입·오류 처리 — 일부 적용, 나머지 P0

**완료:** 평가 점수 디코더, 구체적인 평가 결과 타입, dotenv 오류 중 ENOENT만 허용, 미사용 `mime` 삭제.

**후속 설계:**

- 이미지 provider의 JSON 응답과 다운로드 URL 응답을 검증한다. data 누락·빈 배열·잘못된 바이트·HTTP 실패를 성공 결과로 취급하지 않는다.
- 평가의 cases.json과 환경 변수도 요청 전 검증한다. 잘못된 버전/케이스 제한 때문에 유료 요청이 일부 실행된 뒤 실패하지 않도록 한다.
- 클라이언트에서 `X-Generation-Id`가 없을 때 UUID를 만들어 성공처럼 처리하는 fallback을 제거한다. 서버가 발급한 식별자가 없는 결과는 피드백·수정에 사용할 수 없으므로 응답 오류로 처리한다.
- 생성 도중 provider 오류와 기록 저장 오류를 구분한다. 오류 기록 저장에 실패하더라도 최초 오류 원인을 잃지 않도록 로깅하고, 사용자에게는 내부 응답 내용이나 키를 노출하지 않는다.
- 허용 가능한 실패(예: 피드백 저장 실패)는 UI에 표시하고 이미지 다운로드 자체는 계속 허용한다.

**완료 기준:** malformed JSON, 필수 필드 누락, 429/5xx, 취소, 저장소 실패를 대체 provider/repository로 재현한다. 실제 유료 API 호출 없이 계약·오류 처리 테스트를 수행한다.

## 6. 문서의 역할 혼합 — 우선순위 P2

**설계:**

- README: 제품 설명, 실행, 필요한 환경 변수, 실제 제공 기능, 관련 문서 링크.
- 코드 컨벤션: `code-conventions.md`를 단일 기준으로 사용.
- 설계: 이 문서에서 문제·결정·대상·완료 기준을 관리하고, 구현 시 상태를 갱신한다.
- 운영 안내: 저장 방식, HTTPS, 데이터 보관, 요청/비용 제한, 배포 조건.
- 검증 기록: 실행 날짜, 명령, 결과, 재현 조건. 개인 환경의 Turbopack 실패는 검증 기록에 두고 제품 설명에서 분리한다.
- 이전 `implementation-strategy.md`의 중복 내용을 역할에 맞는 문서로 옮긴 뒤 링크를 갱신하고 통합한다. 이 문서는 현재까지 삭제하지 않았다.

**완료 기준:** README만 읽어도 실행할 수 있고, 구현하지 않은 기능이 현재 제공 기능에 포함되지 않는다. 같은 규칙을 여러 문서에서 서로 다르게 설명하지 않는다.

## 실행 순서

1. P0: 실제 요청 상태 표시와 API/응답 오류 처리. 성공·실패 계약부터 확정한다.
2. P1: 미사용 경로 제거 후 프롬프트 실험을 새 버전으로 분리한다.
3. P2: 확정된 구조와 검증 결과에 맞춰 문서를 통합한다.

각 단계는 독립된 변경으로 검토한다. 컨벤션 정리와 실험 정책 변경을 하나의 검증 결과로 취급하지 않는다.
